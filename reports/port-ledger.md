## User decision and concrete proposed plan

User selected **multiple users, each with private data**. Upstream cannot be safely published as one shared server: stores, credential owners, event bus, background jobs and turn registries are process-wide. Its `read`, `ls`, `find`, `grep` and PDF tools accept filesystem paths under the learner home and absolute paths. Merely switching a data directory per HTTP request cannot provide isolation.

Proposed implementation, pending the repository-required plan approval and login choice:

1. Keep the upstream React/Next interface, prompts, contracts and agent loops. Retain the upstream marketing site as a secondary About surface with original attribution and a clear route back to the browser app. No interface redesign.
2. Put authentication and tenant routing in a small gateway outside the app. Each account owns an opaque server-assigned identifier; user input never selects arbitrary directories, ports, commands or containers. Require authenticated requests for pages, API routes and event streams; reject cross-origin mutations; use secure HTTP-only session cookies and explicit logout. Shared immutable build assets may be cached; user responses must not be shared-cacheable.
3. Give each learner a separate unprivileged application container and persistent private volume, with a shared immutable image. Do not mount the Docker socket, host home or other learner volumes in application containers. Drop capabilities, enable no-new-privileges, bound CPU/memory/process count and temporary storage. Block tenant-to-tenant and host/private-network traffic, including cloud metadata, while preserving provider and research access. Validate the actual network boundary.
4. Start tenant runtimes on demand. Measure warm memory before choosing active-account limits. Idle shutdown must preserve jobs, active turns and persisted records, rather than treating an SSE connection or a timer as proof of activity or quiescence.
5. Build the production image for ARM64 with a supported Node runtime and system Chromium. Keep the existing SVG/PDF native renderers and require actual generated-demo verification. Add only browser adapters needed for native-only behavior. Audit remote subscription callbacks without removing working native/provider variants. Preserve dictation and browser keyboard/clipboard behavior and document browser permission limits.
6. Measure the deployed startup, initial transfer, graph rendering with representative data and session responsiveness. Reduce measured unnecessary eager imports using code splitting while checking visual/interaction parity. Do not rewrite the TypeScript app into Wasm speculatively. Reconsider a targeted Wasm worker only if a reproducible compute bottleneck remains after profiling.
7. Verify two independent accounts through login, provider settings, teaching/practice records, graph, jobs, SSE, logout, restart and persistence. Attempt cross-account requests and filesystem/network reads. Compare desktop/reference and browser UI states at desktop and mobile sizes, including markdown, math, diagrams, maps, quiz/thinking/confidence and generated artifacts. Real provider calls require a user-configured test account; keep offline evidence separate from live-provider proof.
8. Deploy a reversible release on oci-main behind its existing loopback Nginx/Tunnel, publish exact corresponding AGPL source with the deployed release, verify TLS/cache/streaming and repeat important workflows at learn.nix.zone. Record release hashes and rollback steps.

Architecture research: WebAssembly's official use-case list supports embedding compute helpers into existing JS/HTML applications, but does not establish any speedup for this app: https://webassembly.org/docs/use-cases/. The upstream source already has a Node web runtime and native dependencies. Next's installed 16.3.2 documentation (`node_modules/next/dist/docs/01-app/02-guides/self-hosting.md` and `03-api-reference/05-config/01-next-config-js/output.md`) documents standalone output, reverse proxy, streaming and cache boundaries. Docker's security documentation establishes that network connectivity must be restricted explicitly and that exposing Docker control requires strict trusted inputs: https://docs.docker.com/engine/security/.

Approval requirement: root `AGENTS.md` says to investigate, plan and get the plan approved before implementation. Original user authorization already covers deployment and performance/fidelity work. This additional question is specifically for the concrete multi-user design and account/login behavior introduced by the new user preference, not routine build or deployment permission.
